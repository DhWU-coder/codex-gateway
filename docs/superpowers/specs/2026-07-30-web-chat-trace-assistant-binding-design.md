# Web Chat 中间过程归属与折叠设计

## 背景

Web Chat 已经能够实时展示 Codex 的中间回复和工具调用，但当前页面把 Trace 节点直接插在
用户消息之后。视觉上它因此属于用户消息，而不是随后出现的 Codex 回复。

任务完成后，Trace 还可能继续保持展开。原因是运行态节点创建时会通过 `open` 属性自动展开，
浏览器稍后触发的 `toggle` 事件可能在同一个 Trace 对象已经变为完成态后执行，并把这次程序
触发的展开错误地记成用户选择。

## 目标

- 每个用户回合只对应一个 Codex 回复区域。
- 任务运行中先显示 Codex 回复外壳，在其中展开全部中间回复和工具调用。
- 当前正在运行的工具调用继续显示在 Trace 摘要中。
- 任务完成、失败或停止时自动折叠 Trace，并在同一个 Codex 回复区域中显示最终回复。
- 用户可以在任务结束后手动重新展开 Trace。
- 页面刷新后使用持久化的 `assistantMessageId` 恢复相同的归属关系。

## 非目标

- 不修改 App Server 事件协议或 Trace 持久化格式。
- 不改变中间回复、工具分组和最终回复的文本内容。
- 不改变飞书消息展示。

## 消息编排

Trace 已同时保存用户消息 ID `messageId` 和预先分配的 Codex 消息 ID
`assistantMessageId`。页面渲染时分别建立两张索引：

- 用户消息 ID 到 Trace。
- Codex 消息 ID 到 Trace。

遍历消息时：

1. 普通用户消息照常渲染。
2. 用户消息存在 Trace 且最终 Codex 消息尚未出现时，立即在其后渲染一个临时 Codex 回复
   外壳，并把 Trace 放进该外壳。
3. 最终 Codex 消息已经存在时，用 `assistantMessageId` 将 Trace 放进真实 Codex 消息，
   Trace 位于最终回复正文之前。
4. 已经随用户回合提前渲染过的 Codex 消息不再在消息数组的原始位置重复渲染。
5. 无法匹配历史消息的孤立 Trace 仍以临时 Codex 回复外壳展示，避免诊断信息丢失。

这样运行态和完成态始终使用相同的 Codex 视觉语义，同时兼容 SSE 到达顺序和刷新后的持久化
数据。

## 折叠状态

运行态 Trace 强制展开，但这种程序控制的展开不能写入用户展开状态。

创建 Trace 节点时记录它是否已经处于可交互的终态。`toggle` 监听器只允许终态创建的节点
更新 `expandedTraceIds`，从而隔离浏览器延迟派发的运行态 `toggle` 事件。

收到 `message.trace` 事件时，如果状态从 `running` 变为终态，页面还会主动清除该 Trace 的
展开记录。下一次渲染因此必然折叠。任务结束后用户再次点击摘要行，才会把该 ID 写回展开
集合。

## 页面结构

Codex 消息内容区按以下顺序渲染：

1. Trace 折叠区。
2. 最终回复正文。
3. 引用和附件。

临时 Codex 回复外壳没有空正文，只显示头像、Codex 标识、时间和 Trace。内嵌 Trace 取消原来
为独立节点预留的左侧外边距，桌面和移动端都与 Codex 正文对齐。

## 测试

- 页面源码回归测试确认使用 `assistantMessageId` 绑定 Trace。
- 页面源码回归测试确认运行态使用临时 Codex 回复外壳。
- 页面源码回归测试确认终态转换会清理展开状态。
- 页面源码回归测试确认运行态程序展开不会被记录成用户操作。
- 页面源码回归测试确认内嵌 Trace 样式存在。
- 运行完整测试、类型检查和构建，确认没有影响其他渠道。
