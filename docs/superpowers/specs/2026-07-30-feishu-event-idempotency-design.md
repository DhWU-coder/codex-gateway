# 飞书事件快速确认与持久化去重设计

## 问题

飞书长连接要求事件处理函数在 3 秒内结束且不抛出异常。当前事件处理函数会等待 Codex 完成整轮执行，常见耗时超过 3 秒，飞书因此可能重投同一条消息。

现有去重仅使用 `FeishuChannel` 实例内的 `Map`，默认保留 10 分钟。服务重启会清空记录，飞书在 1 小时或 6 小时后重投时也已经超过有效期，因此同一条消息会再次进入 Codex 并产生重复回复。

## 目标

- 飞书 SDK 收到事件后立即完成回调，不等待 Codex 执行。
- 使用消息事件的 `message_id` 做业务幂等。
- 去重记录跨 Gateway 重启保留，并按飞书账户隔离。
- 不改变飞书命令、附件、过程回复和最终回复的现有行为。

## 事件确认

`createFeishuEventClient` 的 SDK 回调只负责把事件交给后台处理并立即返回。后台 Promise 的异常由事件客户端记录，不能重新抛回 SDK。

`FeishuChannel.handleEvent` 仍负责解析、过滤、领取消息和执行完整业务。事件客户端不复制业务错误回复逻辑。

## 持久化去重

新增独立的飞书消息去重存储，默认文件为：

```text
~/.codex-gateway/channels/feishu/<accountId>/handled-messages.json
```

文件路径从账户的 `historyBaseDir` 推导，不增加用户配置项。

记录结构包含版本号和 `message_id -> handledAt` 映射。Channel 收到有效消息后，在第一次异步等待之前同步领取并持久化该 ID，确保并发重复事件无法同时进入执行。

记录默认保留 7 天，并限制最大条数。清理在领取消息时进行；写入采用临时文件加重命名，避免进程退出留下半个 JSON 文件。文件不存在、为空或损坏时按空记录处理，损坏内容会记录警告，不阻断飞书服务启动。

## 失败语义

- 同一个 `message_id` 在保留期内只执行一次。
- 服务在消息执行中崩溃后，该消息仍视为已领取，避免恢复后再次产生重复回复。
- 后台处理失败沿用现有“处理失败”回复和日志。
- 持久化写入失败时记录错误并停止处理该事件，避免在无法保证幂等时继续生成可能重复的回复。

## 测试

- SDK 回调不会等待未完成的业务 Promise。
- 后台 Promise 拒绝时会记录错误且不产生未处理拒绝。
- 同一存储实例会拒绝重复 `message_id`。
- 新建存储实例后仍会拒绝已持久化的 `message_id`。
- 过期记录会被清理，文件条数受上限约束。
- Channel 在重建实例后不会再次执行同一消息。
