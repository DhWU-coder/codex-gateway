# Web Chat 拖拽与粘贴文件设计

## 背景

Web Chat 已支持通过“添加附件”按钮选择多个文件，并在发送消息时依次上传。当前缺少拖拽
和剪贴板粘贴入口，而且前端、HTTP API 与 Manager 都要求消息文本非空，因此不能只发送
附件。

## 目标

- 文件选择、拖拽和剪贴板粘贴统一进入待发送附件队列。
- 文件拖入会话区域时提供清晰且不抖动的投放反馈。
- 粘贴截图或剪贴板文件时不影响普通文字粘贴。
- 允许不输入文字、只发送一个或多个附件。
- 用户可在发送前检查和移除附件。
- 上传或发送失败时保留待发送队列，便于重试。

## 交互设计

### 文件入队

新增统一的 `addPendingFiles` 前端函数。隐藏文件输入框、拖放事件和粘贴事件都调用该函数，
避免三套入口出现不同校验或渲染行为。

入队时执行以下校验：

- 忽略不是 `File` 的项目。
- 拒绝空文件。
- 拒绝单文件超过 30MB。
- 根据文件名、大小、最后修改时间和 MIME 类型过滤当前队列中的重复项。

校验失败通过现有错误 Toast 告知用户；合法文件加入现有附件标签列表。

### 拖拽

整个 Chat 主区域作为投放目标。检测到拖入文件时显示覆盖会话内容的遮罩，文案为
“松开以添加文件”。使用拖拽进入计数器处理子元素之间的 `dragenter` 和 `dragleave`，
避免遮罩闪烁。`drop` 后隐藏遮罩并把 `DataTransfer.files` 加入队列。

普通文本拖拽不被拦截。

### 粘贴

消息输入框监听 `paste`。从 `ClipboardEvent.clipboardData.items` 中提取 `kind === "file"`
的项目并加入队列。事件不阻止默认文字粘贴，因此混合剪贴板中的文字仍可正常进入输入框。

浏览器或操作系统没有向页面暴露文件对象时不做额外处理。

### 发送

发送条件从“文本非空”调整为“文本非空或附件队列非空”。附件仍在用户点击发送后通过现有
上传接口上传，全部上传成功后再提交消息。

纯附件消息在用户历史中保存空文本和附件元数据，不显示伪造的用户文字。Manager 向 Codex
Runner 提交内部提示“请查看并处理用户提供的附件。”，以便 Codex 能够处理附件。若这是
新会话，则使用第一个附件文件名作为会话标题。

## 后端设计

### HTTP API

`POST /api/chat/sessions/:id/messages` 在文本为空时检查 `fileIds`。文本和附件同时为空仍返回
400；存在附件时允许请求进入 Manager。

### Manager

`sendMessage` 先解析并校验附件，再判断消息是否为空。纯附件消息使用独立的内部 Prompt，
但事件载荷、Tracker 和 Session 历史继续保存用户提交的原始空文本。

标题与 Tracker 预览按以下顺序生成：

1. 非空消息文本。
2. 第一个附件文件名。
3. 固定文案“附件消息”。

## 错误处理

- 客户端校验用于即时反馈，服务端 30MB、空文件、所有权和真实路径校验保持不变。
- 任一上传失败时不清空附件队列，也不提交消息。
- 消息提交成功后才清空文本和附件队列。
- 没有有效文件且文本为空时前端不发送请求；绕过前端的空请求仍由服务端拒绝。

## 测试

- Manager 测试：纯附件消息可执行、用户历史保留空文本、Runner 收到内部提示、新会话标题
  使用附件名。
- HTTP 测试：纯附件请求返回 202，文本和附件都为空仍返回 400。
- 页面测试：包含拖拽遮罩、统一入队函数、拖放和粘贴监听器、纯附件发送条件。
- 内联脚本继续通过语法检查。
- 运行 Web Chat 测试、完整测试、类型检查和构建。
- 重启服务后通过真实浏览器验证桌面与移动端布局，并通过真实 HTTP 流程验证纯附件发送。

## 非目标

- 不在文件入队时提前上传。
- 不增加文件预览编辑、目录递归上传或粘贴富文本。
- 不改变服务端单文件 30MB 限制。
- 不让拖入文件自动发送。
